# 07-01 — Ma trận RLS phủ 18 bảng

> Yêu cầu: **TENANT-05**. Quyết định: `15-QuyetDinh/QD-012` §3. Phụ thuộc: không.
> Plan là **hợp đồng + nghiệm thu**, không phải bản nháp code. Viết code bằng TDD, để `tsc` và
> test chấm điểm từng bước.

**Mục tiêu:** chứng minh bằng test tự động rằng nhà hàng A không đọc/ghi/sửa/xóa được dữ liệu của
nhà hàng B trên **cả 18 bảng** mang `tenant_id` — thay vì 2 bảng như hiện nay.

**Cách làm:** fixture tự dựng bằng service-role trong `beforeAll` (UUID cố định, dọn ở `afterAll`);
mọi khẳng định chạy bằng **anon key + phiên đăng nhập thật**. Ma trận viết dạng bảng dữ liệu
`CASES` + `it.each` để thêm bảng sau này chỉ là thêm một dòng.

## Ràng buộc

- **Không bao giờ** dùng service-role để khẳng định quyền — chỉ để dựng/dọn fixture và đối chiếu
  "dòng của B còn nguyên". Test assert bằng service-role sẽ luôn xanh và không chứng minh gì.
- Dùng owner seed sẵn có (`ownerA@pho-viet.test`, `ownerB@bun-bo.test`, `DemoPass123!`). Không tạo
  auth user mới.
- Fixture **idempotent**: chạy lại nhiều lần trên cùng DB không cần dọn tay (dùng `upsert`).
- Tên test tiếng Việt, tên biến/hàm tiếng Anh.

## Hợp đồng (`tests/rls/fixtures.ts`)

```ts
export type TenantKey = "A" | "B";
export function adminClient(): SupabaseClient;
export function fid(key: TenantKey, n: number): string;   // uuid cố định: f1… = A, f2… = B
export const IDX: Record<string, number>;                  // tên bảng → chỉ số thực thể
export const ALT_GROUP = 18;                               // nhóm tùy chọn thứ 2, không gắn món nào
export async function seedFixtures(): Promise<{ tenantA: string; tenantB: string }>;
export async function cleanupFixtures(): Promise<void>;
// đặt trong setup.ts:
export async function tenantIdBySlug(slug: string): Promise<string>;
```

Fixture dựng **đúng 1 dòng mỗi bảng, mỗi tenant**, thành một dây đầy đủ: danh mục → món → nhóm
tùy chọn → bảng nối → khu vực → bàn → phiên bàn → đơn → món trong đơn → tùy chọn món → bill →
dòng bill → thanh toán, cộng đặt bàn, gọi nhân viên, phiếu in, nhân viên PIN (`user_id = null`).

18 bảng: `memberships`, `menu_categories`, `menu_items`, `modifier_groups`, `modifier_options`,
`menu_item_modifier_groups`, `areas`, `tables`, `table_sessions`, `orders`, `order_items`,
`order_item_modifiers`, `bills`, `bill_items`, `payments`, `print_jobs`, `reservations`,
`staff_calls`.

## Cạm bẫy đã biết (rà schema 23/09/2026 — đừng phát hiện lại bằng cách vấp)

- `bill_items.order_item_id` là **ON DELETE RESTRICT**. Teardown phải xóa `payments` →
  `bill_items` → `bills` **trước** `order_items` → `orders`, nếu không Postgres từ chối.
- `tables.qr_token` **unique toàn cục** → fixture của A và B phải khác nhau (`rlsmatrix-A/B`).
- `menu_item_modifier_groups` khóa chính là `(item_id, group_id)`, **không có cột `id`** → mọi chỗ
  trỏ khóa phải tham số hóa tên cột.
- Phép "A insert vào bảng nối của B" cần cặp khóa **chưa tồn tại**, nếu không lỗi trùng khóa chính
  sẽ che mất thứ cần đo là RLS. Đó là lý do có `ALT_GROUP`.
- `memberships.user_id` **nullable** (nhân viên PIN-only) → fixture không phải tạo auth user.
- `update`/`delete` chéo tenant **không sinh lỗi**: mệnh đề `USING` lọc mất dòng trước khi sửa nên
  PostgREST trả 0 dòng. Chỉ `insert` báo lỗi (`42501`, vướng `WITH CHECK`). Cả hai đều đúng —
  đừng sửa test để bắt lỗi ở `update`.

## Test phải có

`tests/rls/fixtures.test.ts` (3):
- hai tenant demo là hai tenant khác nhau
- dựng đủ 2 dòng fixture ở mọi bảng trong `IDX`
- chạy `seedFixtures` lần hai không lỗi (idempotent)

`tests/rls/matrix.test.ts` — 1 test đếm `CASES.length === 18`, cộng 7 phép × 18 bảng:
- đối chứng dương: A đọc dữ liệu của chính A → ≥1 dòng
- A đọc dữ liệu của B → 0 dòng
- B đọc dữ liệu của A → 0 dòng
- A trỏ thẳng id của B → 0 dòng
- A insert dòng mang `tenant_id` của B → **có lỗi** *và* số dòng của B không đổi (đếm trước/sau)
- A update dòng của B → 0 dòng đổi, đối chiếu service-role thấy dòng B **y nguyên**
- A delete dòng của B → 0 dòng xóa, dòng B vẫn còn

Tổng ≈ 127 test cho `matrix`, 130 cho cả thư mục mới.

## Nghiệm thu

```bash
npm run test:rls            # toàn bộ PASS, ≥120 test
npx tsc --noEmit && npm run lint
```

**Đối chứng âm — bắt buộc, không được bỏ.** Một bộ test luôn xanh có thể xanh vì nó không đo gì.
Trên DB test (không phải production):

```bash
psql "$POSTGRES_URL_NON_POOLING" -c "drop policy if exists print_jobs_tenant_all on public.print_jobs;"
npm run test:rls            # các test print_jobs phải ĐỎ
psql "$POSTGRES_URL_NON_POOLING" -f supabase/migrations/0010_print_jobs.sql
npm run test:rls            # xanh lại
```

Lưu output cả hai lần vào `07-01-SUMMARY.md`.

**Cổng CI:** bước `Test RLS` trong `.github/workflows/ci.yml` phải chạy với
`--reporter=json --outputFile=rls-report.json`, đọc `numTotalTests` và `exit 1` nếu `< 120` —
hiện tại `npm run test:rls` trả mã 0 cả khi không test nào chạy. Thêm `rls-report.json` vào
`.gitignore`.

**Fixture dọn sạch:** sau khi chạy, `select count(*) from menu_categories where name like 'RLS-MATRIX-%'`
trả `0`.
